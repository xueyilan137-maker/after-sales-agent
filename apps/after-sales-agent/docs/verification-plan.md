## 第一阶段：商品损坏工程验证（第一层，不调用模型）

1. 核对现有代码、配置、容器和日志；不重新初始化账户、不升级底座。使用固定容器依赖，不为测试盲目新增框架或修改锁文件。
2. 在隔离的临时数据库和记忆目录中编写、运行有意义的业务测试。先完成正常损坏流程，再覆盖未审批执行、审批后证据变化、重复执行、过期 revision、身份隔离、申报期限与审批期限等关键约束。
3. 验证独立 RUN/DEMO 实例可重现，原订单签收及首次申报历史不变。模拟身份/时钟仅用于隔离测试；模拟管理员不能证明真实登录审批链路。
4. 先记录预期结果，再记录实际结果与失败；修复后做针对性回归。代码路径或依赖若可能触发模型网络请求，先阻断或替换相应边界，不能用真实模型排查普通业务错误。

通过条件：正常流程到达预期状态；关键禁止操作被拒绝且不产生额外执行记录；重复执行不重复入账；资料变更后原方案不能继续执行；缺陷与未覆盖项明确列出。测试通过只证明覆盖范围，不代表 Agent 已通过。

## 第二阶段：MCP、身份与工作台接入（第二层，不调用模型）

- 通过固定 DeerFlow 的实际 MCP 加载器检查目录和 schema，确认 12 个服务定义、10 个模型白名单及审批工具缺席；检查两个 Skill 的路径和读取限制。
- 直接调用 MCP，核对可信身份签名的传递、缺失/过期/错误身份拒绝、业务错误返回和工单投影；不得以绕过 interceptor 的直接业务函数调用代替身份集成证据。
- 在现有登录工作台创建独立合成实例，核对资料保存、人工审批、演示执行与回写。实际审批只能经交互式管理员会话；没有可用会话时记录缺口，不伪造登录或直接修改数据库审批。
- 跑通两个重点展示场景：正常损坏闭环；审批后补充证据使旧方案失效，再生成方案、人工审批和执行。重复执行结果作为附加可靠性证据。
- 写入现有业务卷前保存备份；只新增标记清楚的验证实例，不清空历史，不恢复覆盖现有库。备份恢复验证在隔离副本进行。

通过条件：工具发现和调用、身份、人工审批、执行回写有可追踪记录。Skill 注册/可读与模型主动选择 Skill 分开记录，后者留到第三层。接口直接调用证据不冒充真实 Agent 对话。

## 第三阶段：小规模真实 Agent 验证（第三层，先询问用户）

前两层完成并修复阻断项后，给用户展示具体计划：优先一条正常损坏流程，再一条审批失效异常流程，分批推进；用户消息条数不等于模型 API 调用次数。说明预期工具、人工操作节点、累计用量和循环停止条件。预算未定时不得承诺固定金额或把事后 token 检查描述为硬限额。

获准后检查模型是否补问必要资料、引用适用政策、使用正确工具、等待真实人工审批，并在工具拒绝后正确解释和继续。记录线程/run、场景、工具序列、工单/方案/操作 ID、耗时和实际 usage；不可获得的账单费用标记未核对。先检查首条结果，再决定是否继续授权范围内的下一条；超出范围需重新询问，不自动重复付费运行。

产出：正常闭环和关键异常的真实运行证据、失败修复记录、改造后 token 样本。少量样本不用于宣称总体成功率。
