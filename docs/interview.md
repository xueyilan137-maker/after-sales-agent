# 面试讲解提纲

## 一分钟介绍

我基于固定版本 DeerFlow 做了一个售后与工单协同 Agent，复用其运行时、网页、认证、MCP 和 DeerMem，自己实现订单场景、状态机、政策规则、可信身份、审批与幂等执行。所有业务是合成数据；模型负责理解和编排，最终权限和状态由代码核验。项目有真实 Agent 闭环、权限隔离、恢复和有界成本验证，同时保留了工具名错误与修复记录。

## 可以展开的三个问题

**模型说“已批准”怎么办？** 没有审批工具，执行接口只接受真实交互式管理员产生的审批；方案绑定工单版本/证据/政策摘要与真实时钟过期，证据变更后旧审批失效。审批发生在 owner 范围内，不等于团队共享受理系统。

**为什么不直接把整段工具结果喂回模型？** 长会话中旧快照占用上下文，历史正文可在请求副本投影成指针，保留 ID、版本、引用与不能授权当前动作的标记；checkpoint 保留，执行前重读当前状态。测过字符变化与四轮真实费用，但没有证明任意长度成本稳定。

**遇到过什么真实失败？** 普通账号检索时模型把下划线写成连字符，调用被拒绝；错误 ToolMessage 没有 name 又使原停止逻辑漏过。先修复所有 status=error 的尾部工具错误本地停止，再无模型检查完整绑定 schema，添加实际目录全名提示，最后定向真实复验通过。不通过别名或扩大权限掩盖错误，也不改写原失败分数。

## 取舍与下一步

使用 SQLite/本地词法检索/人工确认记忆，让演示规则和来源容易核对；固定底座和 lock 降低复现漂移；单 worker 的暖记忆 IPC 解决每 MCP 初始化开销，但限制水平扩展。下一步可深化工具选择多样本评测、长期资源稳定性、多角色团队受理和外部系统适配，不能把这些描述为已经完成。

展示时优先打开 store.py、identity.py、plugin.py 和针对性测试，再对照 validation.md 的证据层级。不要把底座功能讲成原创，不把本机生产模式称为对外上线。
